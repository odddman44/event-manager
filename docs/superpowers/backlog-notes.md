## #3: 이벤트 "회원만 참가 가능" 옵션 ✅ 완료

> 설계: `docs/superpowers/specs/2026-08-14-members-only-events-design.md`
> 플랜: `docs/superpowers/plans/2026-08-14-members-only-events.md`

**원문 요청:** "주최자에게 '회원만 참가' 가능하도록 주최할 수 있는 옵션이 있으면 좋을 것 같다."

**맥락:** "비회원을 아예 없애야 하나?"라는 고민에 대해, 앱 전체를 회원제로 바꾸는 대신 **이벤트별로 이 옵션을 켤 수 있게** 하는 쪽으로 이미 합의됨(비회원 인프라는 유지).

**#1과의 연결:** `#1`에서 만든 "선택 화면"(비회원으로 계속 / 로그인하고 참여)이 이 기능의 기반이 된다 — "회원만" 이벤트라면 그 선택 화면에서 "비회원으로 계속하기" 버튼 자체를 없애거나 비활성화하면 될 가능성이 높다.

**브레인스토밍 시작 시 물어볼 것:**

1. 스키마: `events`에 `members_only boolean not null default false` 컬럼 하나면 충분해 보이는데, 맞는지?
2. 이벤트 생성/수정 폼(`components/event-form.tsx`)에 체크박스 하나 추가하는 정도로 충분한지, 문구는 어떻게 할지("회원만 참가 가능" 그대로 쓸지)?
3. "회원만" 이벤트를 비로그인 방문자가 열면: `#1`의 선택 화면에서 "비회원으로 계속하기" 버튼을 숨기기만 하면 되는지, 아니면 이벤트 정보 자체를 안 보여주고 로그인부터 강제할지?
4. 서버 측 방어: `joinEvent` 서비스 함수(`src/services/participant-service.ts`)에서 `event.members_only && !userId`면 거절하는 로직이 필요함(클라이언트 UI만 막으면 API 직접 호출로 우회 가능) — 이건 필수로 봐야 함, 별도로 물어볼 필요 없음.
5. 기존에 이미 비회원으로 참여해있던 사람이 있는 이벤트를, 주최자가 나중에 "회원만"으로 바꾸면 그 기존 비회원 참여자들은 어떻게 되는지(그대로 유지? 경고 표시?)

**관련 코드 위치(이미 파악됨):**

- `src/services/participant-service.ts`의 `joinEvent` — 여기서 최종 방어
- `components/event-form.tsx` — 생성/수정 공용 폼
- `components/join-form.tsx`의 `"choice"` 상태(#1에서 신규 추가) — 여기서 비회원 버튼 조건부 숨김

## #5 + #6: 참여자 목록 공개 + 회원/비회원 뱃지 (통합)

**원문 요청:**

- "참여자 리스트를 적어도 회원은 볼 수 있을까?"
- "비회원참가자는 프로필이미지는 디폴트로 두고, 닉네임 옆에 비회원/회원임을 표시하는 뱃지가 있었으면 좋겠다."
- (대화 중 추가) "비회원은 참가자 목록을 어떻게 보게 할 방법 없을까?" → 비회원도 볼 수 있게 하는 쪽으로 확장 검토 필요

**현재 상태(파악됨):** 참여자 목록은 지금 **주최자만** `/events/{id}` 관리 페이지에서 볼 수 있다. 아바타/프로필 이미지는 전혀 표시 안 됨(회원/비회원 구분도 없음, 이름+메모+상태뱃지만). `/join/{token}`(참여자가 보는 화면)에는 참여자 목록 자체가 없음.

**브레인스토밍 시작 시 물어볼 것:**

1. **어디에 목록을 노출할까?** `/join/{token}` 페이지에 새 섹션으로 추가(참여 완료 후에만? 방문 즉시?), 아니면 별도 페이지?
2. **누가 볼 수 있나?** 처음 요청은 "회원만"이었는데 이후 "비회원도" 로 확장 검토 중 — 최종적으로 (a) 회원만 (b) 이 이벤트에 참여한 사람(회원/비회원 무관, 참여자만) (c) 링크를 아는 누구나(참여 여부 무관) 중 어디로 할지 결정 필요. `#3`(회원만 참가 옵션)과 연동해서 "회원만 이벤트는 참여자도 회원만" 같은 규칙이 필요할지도 같이 검토.
3. **표시 정보:** 이름 + 뱃지(회원/비회원) + 기본/실제 아바타는 확정. 메모(memo)도 다른 참여자에게 보여줄지는 미정 — 메모는 "주최자에게 전달하는 말" 성격이라 원래 목적과 다를 수 있음.
4. **아바타 소스:** 회원은 `profiles.avatar_url`(dicebear로 자동 생성되는 것으로 보임, `next.config.ts`의 `api.dicebear.com` remotePattern 확인됨). 비회원은 고정 기본 아이콘. 이 기본 아이콘을 새로 만들어야 함(기존 `/images/default-event-cover.svg`는 이벤트 커버용이라 별개).
5. **실시간성:** 다른 사람이 참여/취소할 때 목록이 자동 갱신돼야 하는지, 새로고침해야 보이면 되는지(Supabase Realtime 쓸지 여부 — 꽤 큰 결정이라 반드시 물어볼 것).

**관련 코드 위치(이미 파악됨):**

- `app/events/[id]/page.tsx`의 참여자 목록 렌더링 부분(주최자용, "c) 참여자 목록" 섹션) — 뱃지/아바타 추가 시 참고할 기존 패턴
- `src/types/index.ts`의 `Participant` interface — `user_id: string | null`로 이미 회원/비회원 구분 가능(별도 컬럼 불필요, `user_id !== null`이 곧 "회원"). 단 아바타 표시하려면 `profiles.avatar_url`을 조인해서 가져와야 함(현재 참여자 조회 쿼리는 join 안 함).

## #7: 이벤트 암호 보호

**원문 요청:** "암호를 걸 선택권을 줘서 암호 입력한 자만 들어오게 하는 기능"

**#3과의 관계:** "회원만 참가"와는 다른 축의 접근 제어다 — 암호는 회원 여부와 무관하게 "링크 URL을 안다"보다 한 단계 더 강한 제약. 두 옵션을 동시에 켤 수 있게 할지(예: 회원이어야 하고 + 암호도 맞아야 함) 아니면 상호 배타적으로 할지는 미정.

**브레인스토밍 시작 시 물어볼 것:**

1. 암호는 **이벤트 정보를 보는 것 자체**를 막는지(암호 입력 전엔 제목/날짜도 안 보임), 아니면 **참여 신청(제출)**만 막는지?
2. 암호 저장 방식: 평문 비교로 충분한지(민감정보 아님, 단순 접근 제어 목적), 아니면 해시해서 저장할지? DB에 평문으로 남기는 게 찜찜하면 해시 권장.
3. 틀린 암호 시도에 대한 제한(무한 재시도 허용? 짧은 딜레이나 횟수 제한?) — 무차별 대입 공격 방어 필요성 검토.
4. 한 번 맞힌 브라우저는 다시 안 물어보게 할지(localStorage에 "이 이벤트는 암호 확인됨" 저장), 아니면 매번 입력?
5. `#3`(회원만)과 동시 적용 가능하게 할지, 아니면 이벤트당 "공개 / 회원만 / 암호" 중 하나만 고르게 할지(라디오 버튼 형태가 더 단순할 수 있음).

## #4: 날짜 범위(여러 날) 모임 지원

**원문 요청:** "모임이 범위로 진행될 가능성이 배제되어 있다" → 확인 결과 **여러 날에 걸친 모임(예: 8/15~8/17 2박3일 캠프)을 표현할 방법이 없다**는 뜻으로 확정됨. 현재 `events.event_date`는 단일 시점(timestamptz) 하나뿐, 종료일이 없음.

**규모가 가장 크다** — 다른 3개와 독립적이고, 스키마 변경 + 날짜를 표시하는 거의 모든 화면(생성/수정 폼, 이벤트 카드, 대시보드, 상세 페이지, 참여 페이지, 어드민)을 손봐야 함.

**브레인스토밍 시작 시 물어볼 것:**

1. 스키마: `event_date` 하나를 유지하면서 `end_date`(nullable)를 추가하는 쪽으로 갈지(단일 날짜 이벤트는 `end_date`가 null), 아니면 완전히 다른 모델(예: 세션 여러 개를 갖는 구조)로 갈지? — nullable `end_date` 추가가 기존 데이터 마이그레이션 없이 가장 간단해 보임.
2. 기존에 이미 만들어진 이벤트(전부 단일 날짜)는 자동으로 `end_date = null`(=단일 날짜)로 처리되면 되는지 확인.
3. 날짜 표시 형식: "8월 15일 ~ 8월 17일" vs "8월 15일(3일간)" 등 UI 문구 확정 필요.
4. 참여자 화면에서 여러 날 중 "이 날만 참여" 같은 부분 참여 개념까지 필요한지, 아니면 그냥 "기간 전체에 참여"만 표현하면 되는지(후자가 훨씬 간단 — 아마 이걸로 충분할 듯).
5. `event_date` 기준으로 정렬/필터하는 기존 로직(`listEventsByOrganizer` 등 `order("event_date", ...)`)이 종료일 개념과 충돌 없는지 — 시작일 기준 정렬 유지하면 문제없어 보임.

**관련 코드 위치(이미 파악됨):**

- `src/types/index.ts`의 `Event.event_date: string`
- `components/event-form.tsx` — 날짜 입력 필드
- 날짜 포맷팅 함수가 여러 파일에 중복 존재(`app/events/[id]/page.tsx`, `components/join-form.tsx` 등 각자 `formatDate` 정의) — 종료일 표시 추가 시 이 중복도 같이 눈에 띌 것

## #8: 로그인 사용자가 참여 링크로 들어와도 앱 헤더/네비게이션이 안 보임

**원문 요청:** "로그인한 사용자는 링크로 들어오고 로그인 하고나면 다른 UI가 보여야 하지 않나. (내 이벤트, 새 이벤트 등이 헤더줄에 보이는 화면)"

**현재 상태(파악됨):** `/join/{share_token}`는 `app/dashboard/layout.tsx`(헤더에 "내 이벤트"/"새 이벤트" 등이 있는 레이아웃)를 전혀 쓰지 않고 루트 레이아웃만 적용된다. 로그인 여부와 무관하게 원래부터 "미니멀한 단독 페이지"로 설계되어 있다(낯선 방문자도 들어오는 공개 페이지라 앱 크롬을 안 보여주려는 의도였을 가능성).

**브레인스토밍 시작 시 물어볼 것:**

1. 비로그인 방문자에게는 지금처럼 미니멀 유지, **로그인 상태일 때만** 헤더를 보여줄지? (그렇다면 `isLoggedIn` prop을 이미 받고 있는 `JoinForm`/페이지에서 조건부로 헤더 컴포넌트를 씌우는 정도로 가능해 보임)
2. 헤더를 보여준다면 `dashboard/layout.tsx`의 헤더를 그대로 재사용할지, 참여 페이지 전용으로 축약된 버전을 새로 만들지?
3. 참여 폼과 헤더 네비게이션(특히 "새 이벤트"로 이동)이 공존할 때, 참여 도중 입력값이 날아가는 문제는 없는지(현재 `#1`에서 방금 추가한 뒤로가기 버튼처럼 상태 보존 신경 필요).

**관련 코드 위치(이미 파악됨):**

- `app/dashboard/layout.tsx` — 재사용/참고할 기존 헤더 패턴
- `app/join/[share_token]/page.tsx` — 레이아웃 미적용 지점, `isLoggedIn`을 이미 서버에서 계산해 내려주고 있음(`#1`에서 추가됨)

## #9: 모임 작성자가 자기 공유 링크로 들어가면 참여자 화면이 아니라 관리 화면으로 가야 하지 않나

**원문 요청:** "모임글 작성자에게는 작성자권한의 화면으로 들어와야 하지 않나 (모임글 수정 삭제 가능한)"

**현재 상태(파악됨):** 참여 흐름(`getJoinPageData`, `JoinForm`) 어디에도 "이 방문자가 `event.organizer_id`와 같은 사람인지" 확인하는 코드가 없다. 작성자가 본인 공유 링크를 열면 일반 참여자와 완전히 동일하게 choice 화면 → 참여 폼을 거치게 된다.

**브레인스토밍 시작 시 물어볼 것:**

1. 작성자가 자기 링크를 열면 **자동으로 `/events/{id}` 관리 페이지로 리다이렉트**할지, 아니면 참여 페이지에 **"이건 당신 모임입니다 → 관리하기" 안내 배너**만 띄우고 원하면 그래도 참여(테스트 삼아?)할 수 있게 둘지?
2. 자동 리다이렉트로 간다면, 작성자가 "내가 참여자로서 어떻게 보이는지" 미리보기하고 싶을 때의 우회 경로가 필요한지(예: 배너 방식이 이 요구를 자연히 커버함).
3. `#3`(회원만 참가 옵션), `#7`(암호 보호)과 겹치는 지점 없는지 — 작성자 감지가 그 두 기능보다 먼저 체크돼야 함(암호 걸린 자기 모임 링크를 열었는데 본인이 암호 입력해야 하면 이상함).

**관련 코드 위치(이미 파악됨):**

- `app/join/[share_token]/page.tsx` — 리다이렉트한다면 여기서 `redirect()` 처리

## #10: 참여자 이름이 무조건 구글/프로필 이름이어야 하는지 (닉네임 참여 검토)

**원문 요청:** "사용자 이름은 무조건 구글에 적은 이름이어야 하는게 좀 그렇다. 별명 참여가 가능하면 좋을텐데.. (단, 모임의 특성상, 실명확인이 안된 유저 참여가 좀 곤란해서 이 부분은 브레인스토밍 필요)"

**맥락:** `#1`에서 로그인 사용자는 `profiles.full_name`으로 이름 입력값을 자동 채워주도록 만들었는데(현재는 그냥 `useState` 초깃값이라 **수정 가능**), 이번 요청은 그 이상 — "애초에 실명/프로필 이름 강제가 맞는지" 자체에 대한 의문. 사용자 본인도 "실명 확인 안 된 사람 참여가 곤란할 수 있다"는 트레이드오프를 이미 인지하고 있어 정책 결정이 먼저 필요.

**브레인스토밍 시작 시 물어볼 것:**

1. 지금도 이름 입력란은 수정 가능한 텍스트 필드라 로그인 사용자도 원하면 다른 이름으로 바꿔서 제출할 수 있는데, 이걸로 충분한지 아니면 "기본값 자체를 프로필 이름이 아니게" 바꾸길 원하는지?
2. 이 모임 서비스의 실명 확인이 필요한 시나리오(정산, 출석 확인 등)와 캐주얼한 익명성이 필요한 시나리오가 공존할 수 있는데, **이벤트별로 주최자가 "실명 필수" 여부를 정하게** 할지(→ `#3`과 비슷한 이벤트별 옵션 패턴), 아니면 앱 전체 정책으로 통일할지?
3. "실명 확인"을 강제한다면 실제로 무엇으로 확인할 건지(구글 로그인 이름 자체도 사용자가 마음대로 바꿀 수 있어 완전한 실명 확인 수단은 아님) — 확인 불가능한 목표라면 애초에 "확인"보다는 "책임 소재 있는 계정 vs 익명 게스트"로 문제를 재정의하는 게 나을 수 있음.

**관련 코드 위치(이미 파악됨):**

- `components/join-form.tsx`의 `name` state — `useState(loggedInName)` (`#1`에서 추가, 수정 가능한 일반 입력 필드)
- `src/services/profile-service.ts`의 `getFullName` (`#1`에서 추가)

## #11: `participants` 테이블의 anon INSERT RLS가 서버 액션을 우회할 수 있음

**발견 경위:** `#3`(회원만 참가 옵션) 최종 브랜치 리뷰에서 발견. 이 브랜치가 만든 회귀는 아니고, 그 이전부터 있던 플랫폼 레이어(RLS) 이슈다.

**문제:** `supabase/migrations/20260628000003_create_participants_table.sql`의 `"비회원 참여 등록"` 정책이 `to anon, authenticated` + `with check (true)`로 `participants` INSERT를 완전히 열어두고 있다. `events`도 `share_token으로 이벤트 공개 조회` 정책이 `using (true)`라 `event_id`를 얻기 쉽다. 즉 브라우저에 노출된 publishable key로 Supabase REST(`POST /rest/v1/participants`)에 직접 요청하면, `src/services/participant-service.ts`의 `joinEvent`(정원 체크, `#3`의 `members_only` 체크 등 모든 서버 방어 로직이 들어있는 곳)를 완전히 건너뛰고 참여자 행을 만들 수 있다.

**영향 범위:** `members_only`뿐 아니라 `max_participants`(정원 제한) 보장도 이미 동일하게 뚫려 있다 — 이번에 새로 생긴 문제가 아니라 원래부터 있던 문제가 `#3`으로 인해 다시 드러난 것.

**브레인스토밍 시작 시 물어볼 것:**

1. INSERT 정책 자체를 없애고 `createParticipant`(`src/repositories/participant-repository.ts`)를 서비스 역할 키(admin client) 경유로 바꾸는 쪽으로 갈지 — 이 프로젝트가 UPDATE/DELETE에는 이미 이런 패턴을 쓴 선례가 있다(`participant-repository.ts` 주석 참고).
2. 아니면 RLS 정책 자체에 조건을 추가해서(`not exists (select 1 from events e where e.id = event_id and e.members_only and user_id is null)`, 정원 체크는 RLS로 표현하기 더 까다로움) DB 레벨에서 최소한의 방어를 겹으로 둘지.
3. 이 작업이 `#3`/`#7`(회원만/암호 보호) 두 기능의 실질적 보장 강도에 직접 걸려있는 만큼, 우선순위를 다른 백로그 항목보다 앞당길지 여부.

**관련 코드 위치(이미 파악됨):**

- `supabase/migrations/20260628000003_create_participants_table.sql` — 문제의 INSERT 정책
- `src/repositories/participant-repository.ts` — `createParticipant`, UPDATE/DELETE의 기존 admin client 패턴
- `src/services/participant-service.ts`의 `joinEvent` — 우회되는 서버 방어 로직들
