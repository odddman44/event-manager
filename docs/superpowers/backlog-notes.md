## #3: 이벤트 "회원만 참가 가능" 옵션

**원문 요청:** "주최자에게 '회원만 참가' 가능하도록 주최할 수 있는 옵션이 있으면 좋을 것 같다."

**맥락:** "비회원을 아예 없애야 하나?"라는 고민에 대해, 앱 전체를 회원제로 바꾸는 대신 **이벤트별로 이 옵션을 켤 수 있게** 하는 쪽으로 이미 합의됨(비회원 인프라는 유지).

**#1과의 연결:** `#1`에서 만든 "선택 화면"(비회원으로 계속 / 로그인하고 참여)이 이 기능의 기반이 된다 — "회원만" 이벤트라면 그 선택 화면에서 "비회원으로 계속하기" 버튼 자체를 없애거나 비활성화하면 될 가능성이 높다.

**브레인스토밍 시작 시 물어볼 것:**

1. 스키마: `events`에 `members_only boolean not null default false` 컬럼 하나면 충분해 보이는데, 맞는지?
2. 이벤트 생성/수정 폼(`components/event-form.tsx`)에 체크박스 하나 추가하는 정도로 충분한지, 문구는 어떻게 할지("회원만 참가 가능" 그대로 쓸지)?
3. "회원만" 이벤트를 비로그인 방문자가 열면: `#1`의 선택 화면에서 "비회원으로 계속하기" 버튼을 숨기기만 하면 되는지, 아니면 이벤트 정보 자체를 안 보여주고 로그인부터 강제할지?
4. 서버 측 방어: `joinEvent` 서비스 함수(`src/services/participant-service.ts`)에서 `event.members_only && !userId`면 거절하는 로직이 필요함(클라이언트 UI만 막으면 API 직접 호출로 우회 가능) — 이건 필수로 봐야 함, 별도로 물어볼 필요 없음.
5. 기존에 이미 비회원으로 참여해있던 사람이 있는 이벤트를, 주최자가 나중에 "회원만"으로 바꾸면 그 기존 비회원 참여자들은 어떻게 되는지(그대로 유지? 경고 표시?)

**관련 코드 위치(이미 파악됨):**

- `src/services/participant-service.ts`의 `joinEvent` — 여기서 최종 방어
- `components/event-form.tsx` — 생성/수정 공용 폼
- `components/join-form.tsx`의 `"choice"` 상태(#1에서 신규 추가) — 여기서 비회원 버튼 조건부 숨김

## #5 + #6: 참여자 목록 공개 + 회원/비회원 뱃지 (통합)

**원문 요청:**

- "참여자 리스트를 적어도 회원은 볼 수 있을까?"
- "비회원참가자는 프로필이미지는 디폴트로 두고, 닉네임 옆에 비회원/회원임을 표시하는 뱃지가 있었으면 좋겠다."
- (대화 중 추가) "비회원은 참가자 목록을 어떻게 보게 할 방법 없을까?" → 비회원도 볼 수 있게 하는 쪽으로 확장 검토 필요

**현재 상태(파악됨):** 참여자 목록은 지금 **주최자만** `/events/{id}` 관리 페이지에서 볼 수 있다. 아바타/프로필 이미지는 전혀 표시 안 됨(회원/비회원 구분도 없음, 이름+메모+상태뱃지만). `/join/{token}`(참여자가 보는 화면)에는 참여자 목록 자체가 없음.

**브레인스토밍 시작 시 물어볼 것:**

1. **어디에 목록을 노출할까?** `/join/{token}` 페이지에 새 섹션으로 추가(참여 완료 후에만? 방문 즉시?), 아니면 별도 페이지?
2. **누가 볼 수 있나?** 처음 요청은 "회원만"이었는데 이후 "비회원도" 로 확장 검토 중 — 최종적으로 (a) 회원만 (b) 이 이벤트에 참여한 사람(회원/비회원 무관, 참여자만) (c) 링크를 아는 누구나(참여 여부 무관) 중 어디로 할지 결정 필요. `#3`(회원만 참가 옵션)과 연동해서 "회원만 이벤트는 참여자도 회원만" 같은 규칙이 필요할지도 같이 검토.
3. **표시 정보:** 이름 + 뱃지(회원/비회원) + 기본/실제 아바타는 확정. 메모(memo)도 다른 참여자에게 보여줄지는 미정 — 메모는 "주최자에게 전달하는 말" 성격이라 원래 목적과 다를 수 있음.
4. **아바타 소스:** 회원은 `profiles.avatar_url`(dicebear로 자동 생성되는 것으로 보임, `next.config.ts`의 `api.dicebear.com` remotePattern 확인됨). 비회원은 고정 기본 아이콘. 이 기본 아이콘을 새로 만들어야 함(기존 `/images/default-event-cover.svg`는 이벤트 커버용이라 별개).
5. **실시간성:** 다른 사람이 참여/취소할 때 목록이 자동 갱신돼야 하는지, 새로고침해야 보이면 되는지(Supabase Realtime 쓸지 여부 — 꽤 큰 결정이라 반드시 물어볼 것).

**관련 코드 위치(이미 파악됨):**

- `app/events/[id]/page.tsx`의 참여자 목록 렌더링 부분(주최자용, "c) 참여자 목록" 섹션) — 뱃지/아바타 추가 시 참고할 기존 패턴
- `src/types/index.ts`의 `Participant` interface — `user_id: string | null`로 이미 회원/비회원 구분 가능(별도 컬럼 불필요, `user_id !== null`이 곧 "회원"). 단 아바타 표시하려면 `profiles.avatar_url`을 조인해서 가져와야 함(현재 참여자 조회 쿼리는 join 안 함).

## #7: 이벤트 암호 보호

**원문 요청:** "암호를 걸 선택권을 줘서 암호 입력한 자만 들어오게 하는 기능"

**#3과의 관계:** "회원만 참가"와는 다른 축의 접근 제어다 — 암호는 회원 여부와 무관하게 "링크 URL을 안다"보다 한 단계 더 강한 제약. 두 옵션을 동시에 켤 수 있게 할지(예: 회원이어야 하고 + 암호도 맞아야 함) 아니면 상호 배타적으로 할지는 미정.

**브레인스토밍 시작 시 물어볼 것:**

1. 암호는 **이벤트 정보를 보는 것 자체**를 막는지(암호 입력 전엔 제목/날짜도 안 보임), 아니면 **참여 신청(제출)**만 막는지?
2. 암호 저장 방식: 평문 비교로 충분한지(민감정보 아님, 단순 접근 제어 목적), 아니면 해시해서 저장할지? DB에 평문으로 남기는 게 찜찜하면 해시 권장.
3. 틀린 암호 시도에 대한 제한(무한 재시도 허용? 짧은 딜레이나 횟수 제한?) — 무차별 대입 공격 방어 필요성 검토.
4. 한 번 맞힌 브라우저는 다시 안 물어보게 할지(localStorage에 "이 이벤트는 암호 확인됨" 저장), 아니면 매번 입력?
5. `#3`(회원만)과 동시 적용 가능하게 할지, 아니면 이벤트당 "공개 / 회원만 / 암호" 중 하나만 고르게 할지(라디오 버튼 형태가 더 단순할 수 있음).

## #4: 날짜 범위(여러 날) 모임 지원

**원문 요청:** "모임이 범위로 진행될 가능성이 배제되어 있다" → 확인 결과 **여러 날에 걸친 모임(예: 8/15~8/17 2박3일 캠프)을 표현할 방법이 없다**는 뜻으로 확정됨. 현재 `events.event_date`는 단일 시점(timestamptz) 하나뿐, 종료일이 없음.

**규모가 가장 크다** — 다른 3개와 독립적이고, 스키마 변경 + 날짜를 표시하는 거의 모든 화면(생성/수정 폼, 이벤트 카드, 대시보드, 상세 페이지, 참여 페이지, 어드민)을 손봐야 함.

**브레인스토밍 시작 시 물어볼 것:**

1. 스키마: `event_date` 하나를 유지하면서 `end_date`(nullable)를 추가하는 쪽으로 갈지(단일 날짜 이벤트는 `end_date`가 null), 아니면 완전히 다른 모델(예: 세션 여러 개를 갖는 구조)로 갈지? — nullable `end_date` 추가가 기존 데이터 마이그레이션 없이 가장 간단해 보임.
2. 기존에 이미 만들어진 이벤트(전부 단일 날짜)는 자동으로 `end_date = null`(=단일 날짜)로 처리되면 되는지 확인.
3. 날짜 표시 형식: "8월 15일 ~ 8월 17일" vs "8월 15일(3일간)" 등 UI 문구 확정 필요.
4. 참여자 화면에서 여러 날 중 "이 날만 참여" 같은 부분 참여 개념까지 필요한지, 아니면 그냥 "기간 전체에 참여"만 표현하면 되는지(후자가 훨씬 간단 — 아마 이걸로 충분할 듯).
5. `event_date` 기준으로 정렬/필터하는 기존 로직(`listEventsByOrganizer` 등 `order("event_date", ...)`)이 종료일 개념과 충돌 없는지 — 시작일 기준 정렬 유지하면 문제없어 보임.

**관련 코드 위치(이미 파악됨):**

- `src/types/index.ts`의 `Event.event_date: string`
- `components/event-form.tsx` — 날짜 입력 필드
- 날짜 포맷팅 함수가 여러 파일에 중복 존재(`app/events/[id]/page.tsx`, `components/join-form.tsx` 등 각자 `formatDate` 정의) — 종료일 표시 추가 시 이 중복도 같이 눈에 띌 것

## 참고: 이번 논의에서 검토했으나 채택 안 한 것

- **앱 전체를 회원제로 전환** — 비회원 인프라(정원 동시성, 크로스 디바이스 재인식 등)에 이미 많은 작업이 들어가 있고, 캐주얼한 모임 초대 용도에는 로그인 강제가 오히려 참여율을 떨어뜨릴 수 있어 채택 안 함. 대신 `#3`(이벤트별 회원만 옵션)으로 대체.
